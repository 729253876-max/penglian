### [Important-2] 客户端没有验证完整 journal 状态机，两个末尾事件即可放行预览

**位置**

- `04-源文件与代码/apps/miniprogram/miniprogram/services/runtime-contracts.ts:169-198`
- `04-源文件与代码/apps/miniprogram/miniprogram/services/edit-trace-presentation.ts:3-30`
- `04-源文件与代码/apps/miniprogram/test/edit-trace-presentation.test.ts:159-165`
- `04-源文件与代码/apps/miniprogram/test/pages.test.ts:405-429`
- `04-源文件与代码/apps/miniprogram/test/pages.test.ts:884-903`

**事实**

`parseEditTraceEvent` 只验证单个事件的形状、payload、phase、copyKey 和 evidenceSource。`alignedJournal` 只验证 taskId、事件数量和从 1 开始的连续 sequence。`successEvidence` 只要求最后两条是 `QUALITY_CHECK_PASSED` 与 `PREVIEW_READY`。

因此以下仅有两条事件的历史会返回 `true`：

```text
sequence=1  QUALITY_CHECK_PASSED  evidenceSource=QUALITY_GATE
sequence=2  PREVIEW_READY         evidenceSource=QUALITY_GATE
snapshot.status=SUCCEEDED, snapshot.lastSequence=2, previewUrl=有值
```

这个历史在服务端 `RepairJournalService` 中应因首事件不是 `ASSET_APPROVED` 而被拒绝，但客户端现有单元测试与页面测试却把该行为当作成功用例。

**影响**

如 API 回归、缓存/代理返回被截断的历史，或客户端遇到非预期服务端实现，小程序仍可以将未经上传批准、诊断、用户方案选择和 provider 处理链证明的 URL 展示为真实成功预览。端到端 fail-closed 不成立。

**最小修复**

1. 在可共享的 contracts/domain 层导出完整 journal validator，或在客户端镜像同一状态机。
2. 在展示成功或失败终态前，必须验证从 `ASSET_APPROVED` 开始的完整前置条件、authority、阶段顺序、方向一致性、最多一次重试和终止规则。
3. 删除“两事件成功链”的正向测试，增加缺少上传、诊断、选择、provider stage 和质量开始事件的反例。

### [Important-3] Task snapshot 缺少跨字段终态不变量，矛盾 snapshot 仍可驱动 UI 终态

**位置**

- `04-源文件与代码/apps/miniprogram/miniprogram/services/runtime-contracts.ts:146-161`
- `04-源文件与代码/apps/miniprogram/miniprogram/services/edit-trace-presentation.ts:17-50`
- `04-源文件与代码/apps/miniprogram/test/runtime-contracts.test.ts:86-95`
- `04-源文件与代码/apps/miniprogram/test/edit-trace-presentation.test.ts:159-182`

**事实**

`parseTaskSnapshot` 分别验证 status、previewUrl、failureCode 和 noCharge 的单字段类型，没有验证它们之间的状态不变量。`failureEvidence` 也不要求 `snapshot.status === "FAILED"`，只在 snapshot 已带 failureCode 时才对比事件 code。

只读定向复现确认：

```json
{
  "contradictorySnapshotAccepted": {
    "status": "SUCCEEDED",
    "previewUrl": "https://example.invalid/p.jpg",
    "failureCode": "FIDELITY_GATE_FAILED",
    "noCharge": true
  },
  "failureFromProcessingSnapshot": {
    "code": "FIDELITY_GATE_FAILED",
    "failedChecks": ["IDENTITY"]
  }
}
```

同理，`FAILED + previewUrl`、非终态携带 previewUrl/failureCode/noCharge 也未被 parser 层禁止。

**影响**

客户端可在 snapshot 与 event journal 彼此冲突时选择性地放行成功或失败界面，无法证明它展示的是服务端唯一、自洽的终态。

**最小修复**

1. `SUCCEEDED`：必须有 `previewUrl`，必须没有 `failureCode` 和 `noCharge`。
2. `FAILED`：必须没有 `previewUrl`，必须有允许的 `failureCode`，且 `noCharge === true`。
3. 非终态：必须没有 `previewUrl`、`failureCode` 和 `noCharge`。
4. `successEvidence` 和 `failureEvidence` 必须同时要求 snapshot 终态、终止事件和完整 journal 三方一致。

**2026-08-15 scoped re-review：CLOSED**

- 生产证据：`runtime-contracts.ts:146-175` 建立 snapshot 跨字段不变量；`edit-trace-presentation.ts:25-58` 要求成功快照无 failure 字段，失败快照必须是 `FAILED`、无 previewUrl、有匹配 failureCode 且 `noCharge=true`，并与终止事件一致。

### [Important-4] 全量 refetch 可改写已接受前缀，并将新 journal 与旧 visible/pending 事件混合

**位置**

- `04-源文件与代码/apps/miniprogram/miniprogram/pages/live/index.ts:66-69`
- `04-源文件与代码/apps/miniprogram/miniprogram/pages/live/index.ts:290-335`
- `04-源文件与代码/apps/miniprogram/miniprogram/pages/live/index.ts:412-445`
- `04-源文件与代码/apps/miniprogram/miniprogram/pages/live/index.ts:463-515`
- `04-源文件与代码/apps/miniprogram/test/pages.test.ts:722-795`
- `04-源文件与代码/apps/miniprogram/test/pages.test.ts:837-860`

**事实**

`fullJournal=true` 时，`acceptEvents` 只验证新数组内 taskId 与 sequence 连续，然后直接用 `incoming` 替换 `allEvents`。它没有要求新 journal 与已接受前缀在 eventId 和内容上完全相同，也没有在替换 `allEvents` 时清空或重建 `visibleEvents` 与 `runtime.pending`。

可复现的序列是：

1. 客户端已接受并展示 `sequence=1,eventId=event-A`。
2. 增量页 parser 失败，触发从 sequence 0 的全量 refetch。
3. 全量响应内含合法连续、但已改写为 `sequence=1,eventId=event-B` 的前缀。
4. `allEvents` 被替换为 B，已展示列表仍保留 A，B 又可进入 pending，屏幕上出现两条冲突的 sequence 1。

当 eventId 相同但内容被改写时，去重逻辑反而会保留旧可见内容，与新 `allEvents` 继续分叉。现有测试覆盖了 gap、重复 sequence、乱序、task mismatch 和一次 refetch，但没有覆盖“新响应合法但改写已接受前缀”。

**影响**

恢复路径不再是 append-only journal。UI 可同时展示两份互相矛盾的真实性记录，而终态判断使用的又可以是另一份 `allEvents`。这与“恢复不补写 sequence、历史不可改写”的门禁直接冲突。

**最小修复**

1. 全量 refetch 后先校验新 journal 的前 N 条与已接受 journal 在完整事件内容上逐条一致；任何改写都 fail-closed。
2. 如确有允许的全量替换语义，必须取消 timer，清空 pending，并仅从新 `allEvents` 原子重建 visibleEvents、summary 和 latestEvent。
3. 增加 eventId 不同的前缀改写、eventId 相同但 payload 改写、事件已可见和事件仍 pending 四类反例。

**2026-08-15 scoped re-review：CLOSED**

- 生产证据：`live/index.ts:72-116` 对 eventId、taskId、sequence、type、phase、occurredAt、visibility、evidenceSource、copyKey 与 payload 做逐字段 JSON 等值比较；`live/index.ts:348-379` 在全量 refetch 前要求保留已接受前缀，通过后取消 reveal timer、清空 pending，并从新 allEvents 同步重建 visible/pending/summary/latestEvent。
