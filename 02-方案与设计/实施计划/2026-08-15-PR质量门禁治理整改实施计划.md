# PR 质量门禁治理整改 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把当前“可绕过的 PR 自动检查”整改为可验证、最小权限、不可误报真实验收范围的 GitHub 合并门禁，并关闭已记录的 CI 安全、稳定性和证据一致性风险。

**Architecture:** 整改分为四个可独立回滚的批次：先冻结并核对外部治理条件，再配置 GitHub ruleset；随后以 TDD 加固 workflow 静态契约与测试进程网络边界；最后处理工具链、监听探针和依赖告警，并用最新 head 的 CI、独立复审和负向绕过验证完成验收。治理写操作与代码提交分开，任何 GitHub 设置变更前都再次取得明确授权。

**Tech Stack:** GitHub repository rulesets / branch protection、GitHub Actions、Windows runner、PowerShell、Node.js 24、npm 11、TypeScript 5.9、Vitest 3、原生微信小程序构建链。

## Global Constraints

- 不重做忠实救片 Tasks 1–9，不扩展产品功能。
- 不自动合并、强推、删除 worktree/分支，不读取或打印 Token/Cookie。
- 不接入真实模型、MySQL、COS、STS、微信正式 AppID、付费 API 或生产部署。
- GitHub ruleset、PR Draft/Ready、权限和 reviewer 配置均为外部状态写操作，执行前必须再次获得用户明确授权。
- “完整文字修复过程”继续只来自实际公开事件与权威证据；任何证据冲突均 fail-closed。
- 13 项 MySQL 与 1 项对象存储环境测试继续标为 `NOT ACCEPTED`。
- 依赖治理不得使用无审查的 `npm audit fix`，不得顺带升级无关依赖。
- 每个代码修复必须 TDD：先看见目标反例失败，再做最小实现并全量回归。
- PR 当前 Ready 但 master 未保护；在 G1 关闭前不得建议合并。

### Task 1: 把 required quality check 写入 GitHub ruleset

**Files:**
- No repository code changes
- External state: GitHub repository ruleset for `refs/heads/master`

**Interfaces:**
- Consumes: Task 0 的用户授权与 reviewer 可用性。
- Produces: active ruleset、可审计 JSON 快照和负向绕过验证。

- [x] **Step 1: 导出现有治理状态**

```powershell
gh api repos/729253876-max/penglian/branches/master/protection
gh api repos/729253876-max/penglian/rulesets
```

Expected: 保存响应摘要到项目复审记录；不得把 404 `Branch not protected` 当命令成功后的已保护状态。

- [x] **Step 2: 生成最小 ruleset 提案**

提案精确目标：

- target：branch；include：`refs/heads/master`
- enforcement：active
- require pull request before merging
- required status check context：`quality-gate`，要求最新提交成功
- require conversation resolution
- block force pushes
- block branch deletion
- bypass actors：默认空；任何管理员 bypass 必须单独列出并获批
- required approvals：仅当 `INDEPENDENT_REVIEWER_AVAILABLE=true` 时设为 1
- dismiss stale approvals：仅在启用 required approvals 时开启

Expected: 先展示 JSON/界面值，不执行 POST/PUT。

- [x] **Step 3: 经再次确认后创建 ruleset**

使用 GitHub API 或仓库设置页执行一次最小写操作。不得与 PR 合并、review 或权限邀请混在同一命令中。

- [ ] **Step 4: 只读回读并做负向验证**（`BLOCKED_NEGATIVE_RULESET_TEST`，无可复用 dry-run/evaluation）

```powershell
gh api repos/729253876-max/penglian/rulesets
gh pr view 1 --repo 729253876-max/penglian --json mergeStateStatus,statusCheckRollup,reviewDecision
```

负向验证必须选择一个经用户单独批准的安全方案：

1. GitHub rule insights / rule evaluation 显示缺失或失败的 `quality-gate` 会阻断 merge；或
2. 创建只含无害文档提交的临时测试 PR，在 check 未产生或人为取消时只读观察 `mergeStateStatus` 和 ruleset evaluation，验证后保留审计记录；临时分支的创建和删除分别需要授权。

只读命令本身不能代替负向场景。若没有可用的 rule evaluation/dry-run 且未获批临时测试 PR，记录 `BLOCKED_NEGATIVE_RULESET_TEST`，不得宣称门禁不可绕过。若 GitHub 套餐或权限不支持 ruleset，记录 `BLOCKED_RULESET_UNAVAILABLE`，不得用文字约定冒充技术门禁。
