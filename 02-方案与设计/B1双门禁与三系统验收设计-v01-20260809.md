## 1. 已确认背景

阶段 B1 的身份、授权、会话与任务归属代码已完成原实施阶段的仓库侧自动化验证；
双门禁实施 Tasks 1–4 也已提交至 `d2a10f3`。不过，真实 MySQL 集成测试、正式
AppID IDE 证据和手机端验收尚未完成。当前验收方案修订针对四个问题：

1. 小程序 API 地址硬编码为 `http://127.0.0.1:3100`；真机中的该地址指向手机自身。
2. 修订前两份微信工程曾使用 `touristappid`；双门禁 Task 3 已替换为正式 AppID，
   但仍没有正式 AppID 的 IDE 编译、preview 或真机证据。
3. 原计划把应用连接池重建描述成 MySQL 重启，证据范围被扩大。
4. B1 要求先完成真机验收才允许 B2，但真机需要手机可访问的非生产 API 入口，
   形成阶段循环依赖。

本设计只修订验收架构和验收环境配置，不降低生产发布门槛，也不授权创建腾讯云
资源、购买服务、上传真实用户图片或执行生产发布。

## 2. 采用方案：代码门禁与环境门禁分离

### 2.1 B1-CODE：代码与数据层验收

以下证据全部通过后，B1 代码可以完成最终审查并集成至 `master`：

- TypeScript 类型检查、全量 Vitest、小程序运行时隔离验证和微信构建通过；
- 6 项真实 MySQL 8 集成测试全部实际执行并通过，不允许 skipped；
- MySQL 测试只使用名称匹配 `photo_ai_b1_test...` 的专用测试库；
- 并发登录、refresh 单赢家、最多 5 个活跃设备且第 6 个淘汰最旧会话、连接池
  重建后的持久性和撤销持久性通过；
- B1 全分支最终审查无 Critical 或 Important 问题；
- 已延期的 readiness timeout、无障碍属性和错误文案 Minor 得到明确裁决；
- 验证记录准确区分 PASS、SKIPPED、NOT RUN 和 BLOCKED。

`B1-CODE` 通过后允许开始 B2 的本地代码、接口抽象、模拟器和契约测试，但不自动
授权云资源、真实图片、正式 AppID 外部操作或发布。

### 2.2 B1-ENV：正式微信与三系统环境验收

以下证据全部通过后，B1 环境门禁完成：

- 正式 AppID 工程可编译、预览，并连接到受控的非生产 API；
- Android、iOS、HarmonyOS 三类系统完成规定的核心身份流程；
- AppSecret 只存在于受控后端进程或密钥管理系统，不进入聊天、Git、截图或日志；
- 验收使用专用账号、专用数据库和非生产数据；
- 设备、操作系统、微信版本、时间和结果均写入永久验证记录。

`B1-ENV` 是任何生产发布、真实用户身份接入和真实图片上传的前置门禁，但不再阻塞
`B1-CODE` 集成以及 B2 的无外部资源实现。

## 3. 验收环境配置设计

### 3.1 API 地址

- 小程序不得继续把 `127.0.0.1` 作为唯一 API 地址。
- API 地址由明确的构建期验收配置产生，不能从用户输入或远程响应动态覆盖。
- 本地 `touristappid` 模式只允许开发机 localhost。
- 正式 AppID 验收模式必须使用手机可访问的受控地址；可以是获批准的局域网调试
  地址或非生产 HTTPS/CloudBase 入口。
- 发布模式只允许获批准的 HTTPS 域名或微信云托管私有链路。
- API 地址属于非秘密配置；数据库密码、AppSecret 和云密钥不得进入小程序包。

### 3.2 AppID

- 正式 AppID `wx4f7678cc595d276b` 不是秘密，可用于正式验收工程配置。
- `touristappid` 只能保留在明确的本地开发配置或测试夹具中，不得作为正式验收
  证据来源。
- 两个可导入微信工程必须使用同一验收身份，避免打开不同工程根得到不同结论。

### 3.3 Refresh 可执行性

- 正式产品访问令牌仍为 2 小时，刷新会话最长 30 天。
- 非生产验收环境允许使用显式 `ACCEPTANCE_MODE=1` 的短访问令牌寿命，以便三类
  系统在合理时间内触发真实 refresh。
- 生产环境必须拒绝 `ACCEPTANCE_MODE=1`；验收模式不得改变刷新令牌总寿命、设备
  上限和撤销语义。
- 验收记录必须写明实际 TTL、触发时间和 refresh 前后的会话结果。

## 4. 三系统验收矩阵

### 4.1 每个系统都必须执行

Android、iOS、HarmonyOS 分别执行：

1. 正式 AppID 打开小程序；未同意隐私与元数据处理前不能发起登录；
2. 显式同意后完成首次登录；
3. 关闭并重新打开小程序后会话仍可用；
4. 在验收 TTL 到期后触发 refresh，并由原请求自动重试成功；
5. 退出当前设备后受保护请求被拒绝并返回隐私登录入口；
6. 账户删除入口可见、确认步骤完整。

每条证据记录设备型号、系统名称与版本、微信版本、原生/兼容运行形态、测试账号
代号、开始与结束时间、预期结果、实际结果和证据文件路径。

### 4.2 多设备场景

- 从三类系统中任选两台真实设备验证第二设备登录、当前设备退出和全部设备退出。
- 从三类系统中选择一台，使用可重建的专用账号执行一次真实账户删除，并验证全部
  会话立即撤销；其余两类系统只验证删除入口和确认步骤，避免无必要地消耗账号。
- 第六设备淘汰由真实 MySQL 集成测试承担，不要求准备六台物理手机。
- 若真实设备结果与 MySQL 集成结果冲突，以真实设备故障为准，停止验收并定位根因。

### 4.3 HarmonyOS 证据边界

- 必须记录该微信版本是原生 HarmonyOS 应用还是 Android 兼容层运行。
- 原生 HarmonyOS 与兼容模式是两类不同证据，不能互相替代或合并写成“鸿蒙通过”。
- 若目标 HarmonyOS 版本没有可用的正式微信、小程序调试能力或测试设备，状态记为
  `BLOCKED_EXTERNAL`，不得伪装成 PASS；由用户决定调整目标版本、设备或发布范围。
- HarmonyOS 验收不得默认沿用 Android 结果，即使两者共享部分运行时实现。

## 5. MySQL 证据边界

- 当前测试中的 pool 关闭与重建只称为“应用连接池重建”，不称为“MySQL 重启”。
- readiness query 的 `1500ms` 是传给 mysql2 的 query inactivity timeout，不是端到端
  wall-clock deadline；DNS、连接池排队和底层建连仍需真实环境观测。
- B1 不要求为了验收主动重启托管 MySQL 实例；数据库实例重启、主备切换和灾难
  恢复属于后续基础设施可靠性验收。
- 测试账号只需要四张身份表的最小迁移、读写和清理权限，不使用生产库账号。
- 测试前后都要核对数据库名；测试只清空专用库的身份表，不删除数据库。

## 6. 状态、文档和 Git 规则

- 主工作区与 B1 worktree 的 dirty 状态必须分别记录，不能只记录 HEAD。
- `HANDOFF.md`、B1 实施计划、Task 7 报告和永久验证记录使用同一套双门禁术语。
- Task 7 现有三项未提交文件在修订前保持原样；不得清理、覆盖或误提交到 master。
- 每个验收命令记录工作目录、提交、退出码、通过/跳过数量和外部限制。
- `B1-CODE` 与 `B1-ENV` 分别判定，任何一个未通过都不得宣称“B1 全部验收完成”。

## 7. 成本与外部依赖

继续验收前需要：

- 一个 MySQL 8 专用测试库和最低权限账号；
- 一个手机可访问的非生产 API 入口；
- 正式 AppID 的开发/测试权限和不落盘 AppSecret 注入方式；
- Android、iOS、HarmonyOS 测试设备；
- 至少两个微信测试账号，多设备与删除流程建议使用可重建的专用账号。

可能成本包括 MySQL/云托管按量费用、三类设备获取与维护、HarmonyOS 原生微信
可用性等待、测试账号管理、域名备案与 HTTPS 证书。任何付费、资源开通、扫码、
正式登录或外部提交仍需用户另行明确批准。

## 8. 非目标

- 本设计不实现 B2 上传、COS 或内容审核。
- 不创建腾讯云资源，不选择图像供应商，不处理真实用户图片。
- 不验证 MySQL 实例故障切换、容灾或备份恢复。
- 不把仓库自动化、模拟器编译或 Android 兼容模式扩大为三系统真机通过。

## 9. 验收设计完成标准

- 双门禁定义无循环依赖；
- 三系统矩阵可实际执行且不会要求六台物理设备；
- API 地址、AppID、AppSecret 和验收 TTL 的秘密边界清晰；
- MySQL 连接池证据不再被扩大为数据库实例重启；
- 未批准的费用、云资源和外部动作保持禁止；
- 后续实施计划能以测试先行方式逐项修改代码、文档和验收记录。
