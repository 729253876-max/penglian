## 1. 决策摘要

第一增强切片只聚焦“重要人像忠实救片”，老照片修复作为紧随其后的第二切片。采用两步交付：

1. 先完成可测试的产品闭环，包括真实上传资产衔接、自动诊断、两档方案、完整文字修复实况、前后对比、质量拒绝、一次有限重试和失败不扣权益语义。
2. 再在隔离环境中评估候选预训练模型或国内供应商。只有真实质量、合规、时延和成本同时过门禁，才能进入正式链路。

本切片不训练自有模型。当前差异化来自忠实修复标准、完整文字实况、质量拒绝机制和真实用户验证，而不是模型权重归属。

## 2. 目标与非目标

### 2.1 目标

- 让用户无需提示词即可完成重要人像的自然救片。
- 在处理前明确哪些内容会调整、哪些人物与构图元素必须保护。
- 用完整、连续、可恢复的文字记录展示实际发生的修复过程。
- 只有通过忠实度质量门禁的候选结果才能生成水印预览。
- 质量失败时最多真实重试一次；仍失败则拒绝展示并明确不扣权益。
- 供应商或模型可以替换，业务流程与用户事件契约不依赖某一模型。

### 2.2 非目标

- 不开放老照片修复、物体消除和泛画质增强入口。
- 不新增瘦脸、换脸、妆容生成、背景替换和创意写真。
- 不训练自有基础模型，不直接把第三方模型写死进产品。
- 不复制无明确许可证的 GitHub 代码。
- 不把测试替身输出当作真实修图质量证据。
- 不接入境外 API 或上传真实用户照片，除非重新说明外传目标、数据类型、删除条款并获得批准。
- 不改变 Task 9 真实云、正式 AppID、弱网和 Android/iOS 真机验收门禁。

## 3. 路线选择

### 3.1 采用：适配器加质量门禁

保留现有 `ImageProvider` 边界，扩展为诊断、候选处理、质量检查、有限重试与降级结果。第一步使用确定性实现和测试替身完成产品闭环，第二步再替换为真实模型适配器。

优点是测试边界清晰、不绑定供应商、可以在候选结果不可信时拒绝展示，并与当前 TypeScript/Fastify/原生微信小程序架构一致。

### 3.2 暂不采用：直接模型接入

直接接入 GFPGAN 或第三方 API 虽能较快生成图片，但会同时引入身份漂移、境外外传、成本、许可证归因和供应商锁定风险。GFPGAN 官方资料也明确提示某些版本可能轻微改变身份，因此不能作为忠实修复保证。

### 3.3 暂不采用：新增 Python 自建流水线

OpenCV、CLAHE、Gamma、人脸保护和划痕修复等思想值得在老照片第二切片评估，但当前新增 Python、OpenCV、Dlib 与模型部署体系会扩大维护面，不适合作为第一切片前置条件。

## 4. 用户流程

### 4.1 上传完成

- 展示原图安全缩略图、私密上传状态和元数据清理结果。
- 主操作为“开始分析这张照片”。
- 不在用户确认前启动收费或高成本处理。

### 4.2 照片诊断

- 根据真实检测结果逐条显示面部曝光、背景高光、肤色、轻度噪点或模糊等问题。
- 展示保护项：本人特征、五官、脸型、发型、服饰、姿势、主体数量和主要构图。
- 不显示供应商隐藏推理，不用“AI 正在思考”等虚构表达。

### 4.3 方案确认

提供两档受控方案：

- **自然救片（默认推荐）**：优先保持本人、真实肤质与现场氛围。
- **清晰救片**：在忠实边界内提高适度清晰度，并提示可能暴露原图噪点。

每档方案必须同时写清“会调整什么”和“明确不调整什么”。

### 4.4 修复实况

- 页面中心突出当前实际步骤。
- 已发生的文字事件按连续序号保留，不因新步骤出现而消失。
- 默认逐条显示；“减少动态效果”开启后立即显示全部已发生事件。
- 用户可展开从上传到当前时刻的完整修复记录。
- 离开再进入时从服务端事件账本恢复，不重播不存在的步骤。

### 4.5 结果

- 首屏提供带水印的原图/结果对比。
- 只展示实际通过的忠实度检查项。
- 完整修复记录在结果页继续可见。
- 修复项可以关联文字解释，但不得伪造无法证明的像素级因果关系。
- 第一阶段不出现虚假购买成功、高清已解锁或可发布文案。

## 5. 完整文字修复实况

完整文字实况是 P0 产品能力，不是加载动画。最终预览必须存在完整、顺序正确且与实际执行相符的记录。

### 5.1 可见阶段

1. 上传与隐私处理：私密上传、元数据清理、格式尺寸与安全检查。
2. 照片诊断：实际检测到的问题与需要保护的结构。
3. 方案确定：用户选择、调整边界与明确禁止项。
4. 实际修复：只有具备回执或项目执行证据的调整步骤。
5. 忠实度检查：身份、五官脸型、主体、服饰、构图、非目标区域和伪影检查。
6. 结果与异常：预览生成、真实重试、停止原因和权益处理。

### 5.2 事件字段

每条记录至少包含：

- `eventId`：唯一标识。
- `taskId`：所属任务。
- `sequence`：任务内连续序号。
- `phase`：上传、诊断、方案、修复、检查或交付。
- `type`：严格枚举的事件类型。
- `copyKey`：审核过的用户文案键。
- `payload`：按事件类型严格校验的载荷。
- `occurredAt`：服务端真实发生时间。
- `evidenceSource`：系统检测、用户选择、供应商回执或质量门禁。
- `visibility`：预览可见或解锁后可见。

### 5.3 真实性规则

- 事件验证从两套固定序列升级为“状态机 + 单事件规则 + 必要前置条件”。
- 上传事件与任务事件在界面合并呈现，底层仍保持独立数据边界。
- 供应商可以提交处理回执，不能自行宣布项目质量门禁通过。
- 身份、构图和最终放行事件只能由项目质量门禁产生。
- 前端动画只控制展示节奏，不创造、补写或改变事件。
- 未知事件、序号缺口或非法载荷必须停止完成宣称并安全刷新，不能拼凑过程。
- 可复制的简洁摘要不得包含图片地址、模型凭据、内部供应商参数或其他隐私信息。

## 6. 技术架构

沿用 TypeScript、Fastify、原生微信小程序、MySQL/COS 阶段设计和现有 `ImageProvider` 边界，不为第一切片新增 Python 服务。

### 6.1 服务单元

- `PortraitDiagnosisService`：产生可验证的问题清单和保护项。
- `PortraitPlanService`：从诊断和用户选择生成自然/清晰受控方案。
- `ImageProvider`：生成候选结果；实现可以是测试替身或真实模型适配器。
- `PortraitQualityGate`：独立判断候选结果是否允许展示。
- `RepairJournalService`：把上传、诊断、方案、修复、检查、重试和交付事件合并为完整记录。

每个单元通过明确接口通信，供应商原始字段不得泄漏到小程序业务契约。

### 6.2 数据流

```text
私密上传完成
→ 读取已审核且属于当前用户的照片资产
→ PortraitDiagnosisService 生成真实诊断
→ 固化人物与构图保护项
→ PortraitPlanService 返回两档方案
→ 用户确认
→ 创建异步处理任务
→ ImageProvider 生成候选结果
→ PortraitQualityGate 检查
→ 通过：生成水印预览并记录放行事件
→ 未通过：最多真实重试一次
→ 再失败：拒绝下发候选结果并记录不扣权益
```

小程序只传服务端资产 ID 和受控方案标识，不接收 COS 永久地址、供应商密钥或原始模型参数。

## 7. 忠实度质量门禁

第一步使用确定性检测器和测试夹具验证机制；第二步使用真实照片和真实模型形成质量证据。

候选结果至少检查：

- 人脸数量不变。
- 主人物身份相似度达到经项目样本校准后冻结的阈值。
- 五官、脸型、姿势和服饰无明显结构漂移。
- 主体与主要构图无非预期变化。
- 非目标区域变化在允许范围内。
- 未生成额外人物、文字、饰品或无依据细节。
- 无明显过度磨皮、蜡化、重影或伪影。
- 文件可解码，尺寸、方向和色彩空间合规。

产品级 GO/NO_GO 门禁沿用：

- 身份/主体结构通过率不低于 95%。
- 严重缺陷率不高于 5%。
- 相对原图偏好不低于 65%。
- 相对竞品偏好不低于 45%。
- 愿意保存或分享不低于 60%。
- 失败调用、重试、存储、带宽和退款风险全部计入贡献毛利。

模型指标阈值不得照抄论文、GitHub 示例或供应商宣传值，必须以项目代表性样本校准。

## 8. 模型策略：当前不训练自有模型

### 8.1 当前路径

- 第一步使用确定性实现和测试替身，验证产品闭环和拒绝机制。
- 第二步在隔离环境比较预训练模型或国内可用供应商。
- 真实接入通过 `ImageProvider` 适配器完成，不改变产品事件和质量门禁。
- 模型候选至少审查代码许可证、权重许可证、训练数据声明、境内可用性、删除条款、时延、显存、失败率和综合成本。

### 8.2 必做但不属于训练的工作

- 校准自然度、清晰度、身份相似度与非目标区域变化阈值。
- 校准不同年龄、肤色、眼镜、帽子、妆容、遮挡和多人边界。
- 建立匿名编号的同图盲测集和失败案例分类。
- 固化模型版本、推理参数、预处理和后处理版本，确保结果可复现。

### 8.3 轻量微调的触发条件

只有同时满足以下条件，才另立规格评估 LoRA、轻量微调或专用后处理模型：

1. 预训练候选在同一高价值场景持续出现可复现的系统性失败。
2. 该失败无法通过受控参数、预处理、后处理、路由或质量拒绝解决。
3. 已取得训练用途的单独、明确、可撤回授权；默认产品处理授权不能代替训练授权。
4. 数据量、覆盖度、标注质量和偏差评估足以支持目标。
5. 模型、基础权重、训练数据与输出权利允许目标商业用途。
6. 已有隔离训练环境、访问控制、删除机制、审计记录和预算。
7. 微调带来的质量或成本收益能通过盲测和单位经济门禁。

### 8.4 从零训练

V1 不从零训练人像修复基础模型。RTX 4060 8GB 可以承担有限推理和部分轻量实验，但不作为从零训练高质量人像修复模型的可行依据；硬件变化后仍需重新评估数据、预算和运维能力。

## 9. 错误与降级

- 图片质量不足：允许用户知情后继续，但不保证达到清晰预期。
- 未检测到合适人像：停止人像流程并建议换图，不自动转成生成式处理。
- 多人主体不明确：要求用户重新选择或换图，不猜测主角。
- 供应商超时：只记录真实超时、重试和停止，不补写未发生步骤。
- 忠实度失败：候选结果不下发，最多真实重试一次。
- 重试仍失败：提示“无法在保持本人特征的前提下完成”，不扣权益。
- 页面断开：按事件序号恢复，不重复提交、创建任务或扣费。
- 未知事件或序号缺失：停止完成宣称并重新获取服务端账本。

## 10. 测试与验收

### 10.1 自动化

- 合同：事件类型、阶段、文案键、载荷和证据来源严格匹配。
- 状态机：诊断、确认、处理、检查、重试、成功和失败路径。
- 安全：跨用户资产、伪造任务、未知供应商事件和签名地址泄漏。
- 前端：逐条显示、减少动态效果、完整记录、断线恢复、重复事件去重。
- 错误：无人像、多人不明确、质量不足、超时和身份检查失败。
- 生成物：TypeScript 与微信运行时代码一致，构建和无外部模块运行时验证通过。

### 10.2 真实样本与设备

- 场景：逆光、偏暗、肤色偏灰、轻度噪点和轻微模糊。
- 人群：不同年龄、肤色、眼镜、帽子、妆容、遮挡、单人、双人和多人。
- 质量：原图、本项目和竞品匿名同图盲测。
- 网络：Wi-Fi、移动网络和中断恢复。
- 设备：正式 AppID 下 Android 与 iOS 真机；未完成前不得宣称真实环境通过。
- 成本：成功、失败、重试、存储和带宽均纳入单张综合成本。

### 10.3 阶段结论边界

- 第一步通过只能表述为“产品闭环与质量拒绝机制通过自动化验证”。
- 第二步只有在真实模型、真实样本、真实成本与适用环境通过后，才能表述为“候选能力通过质量与成本门禁”。
- 未完成真实 COS、正式 AppID、弱网和真机验收前，产品仍不可发布。

## 11. GitHub 参考治理

- `Nutlope/restorePhotos` 的 MIT 许可允许在满足许可条件时参考代码，但本切片优先借鉴上传—处理—结果流程，不直接移植其 Next.js、Replicate、Bytescale、Auth.js 或境外托管架构。
- `TencentARC/GFPGAN` 代码为 Apache-2.0；模型权重及依赖仍需逐项核查。官方身份变化风险必须进入质量门禁，不能用模型名代替忠实保证。
- `cl973/image-restoration-agent` 可参考人脸保护、划痕处理、CLAHE 和 Gamma 的算法思想；截至本次公开页面核对未确认明确许可证，因此不复制其代码。
- 任何代码级复用都必须记录仓库、固定提交、文件、许可证、修改范围和归因要求，并经过依赖与安全审查。
- 不克隆、不安装、不运行第三方仓库，直至另行完成风险说明并取得批准。

## 12. 规格自审

- **完整性检查**：正文不存在未完成章节、空白模板字段或模糊的后续补写指令。
- **一致性检查**：第一切片只开放重要人像；老照片仍为第二切片；文字实况只展示真实事件；模型与供应商保持可替换。
- **范围检查**：不引入支付实现、生产云资源、自有模型训练或新 Python 服务。
- **歧义检查**：“不训练”不等于不做参数校准；轻量微调必须满足第 8.3 节全部触发条件并另立规格。
- **验收边界**：自动化闭环、真实模型质量和正式环境发布是三道独立门禁，不互相替代。
