# PR 合并前质量门禁设计

> 版本：v01
>
> 日期：2026-08-14
>
> 适用 PR：`729253876-max/penglian#1`
>
> 当前分支：`codex/v1-faithful-portrait-rescue`

## 1. 目标

把已经在本地通过的自动化门禁复现到 GitHub，并在 PR 转为 Ready 前完成独立全差异复审。本阶段只提高变更的可验证性，不扩展产品功能，不自动合并或发布。

## 2. 已确认边界

- 当前 Draft PR 可合并，但尚无 GitHub Actions 检查，也没有已完成的独立全差异复审。
- 现有本地证据为：全仓 typecheck 通过；Vitest 640 passed、14 skipped、0 failed；小程序 runtime verification、WeChat TypeScript build 和 `git diff --check` 通过。
- 14 项跳过包括 13 项缺少 `MYSQL_INTEGRATION_URL` 的 MySQL 集成测试，以及 1 项对象存储环境条件测试；它们维持 `NOT ACCEPTED`，不能表述为真实 MySQL/COS 验收通过。
- 真实模型、真实成本、正式 AppID、微信 IDE、真机、弱网和发布不属于本阶段。

## 3. 方案选择

采用“最小可信 CI”：覆盖现有本地门禁，但不引入云凭据、真实图片、模型调用或部署。未采用只运行 typecheck/Vitest 的极简方案，因为它无法覆盖小程序运行时隔离和微信构建；未采用真实环境 CI，因为当前缺少授权、凭据、成本和数据治理前提。

## 4. CI 设计

### 4.1 触发与权限

- 仅在目标为 `master` 的 `pull_request` 上自动触发，并允许 `workflow_dispatch` 手动触发。
- 工作流顶层权限固定为 `contents: read`。
- 不使用 `pull_request_target`，避免让来自 PR 的代码在高权限上下文执行。
- 不读取 GitHub Secrets，不授予写仓库、发布包、部署或云资源权限。

### 4.2 依赖与运行目录

- 使用 GitHub 托管的 Windows runner，以匹配项目现有 `npm.cmd` 命令和微信构建路径行为。
- 固定 Node.js 主版本，并以 `04-源文件与代码/package-lock.json` 为缓存和依赖锁定依据。
- 在 `04-源文件与代码` 中运行 `npm.cmd ci --ignore-scripts`；禁止执行依赖安装脚本，禁止使用会改写 lockfile 的安装方式。
- 所有第三方 Actions 必须固定到经人工核对的完整 commit SHA；不能只引用浮动 tag。

### 4.3 门禁命令

按下列顺序运行，任一步非零退出都使 CI 失败：

1. `npm.cmd run typecheck`
2. `npm.cmd test -- --run`
3. `npm.cmd run verify:miniprogram-runtime`
4. `npm.cmd run build:wechat -w @photo-ai/miniprogram`
5. `git diff --check origin/master...HEAD`；checkout 必须固定为 PR head 并提供完整历史，避免无范围命令只检查干净工作区而形成伪门禁。

CI 不配置 `MYSQL_INTEGRATION_URL` 或对象存储凭据。环境条件测试保持 skipped/NOT ACCEPTED；工作流日志和 PR 说明必须保留这一边界。

### 4.4 明确禁止

- 不连接真实 MySQL、COS、STS 或模型服务。
- 不上传用户照片、提示词、项目上下文或测试素材到第三方服务。
- 不运行部署、发布、付费调用、数据库迁移或远程写操作。
- 不为了 CI 变绿而删除测试、改写真实失败为跳过，或放宽身份一致性、证据权威和 fail-closed 门禁。

## 5. 独立复审设计

GitHub CI 全绿后，对 `master...codex/v1-faithful-portrait-rescue` 完整差异做独立复审，重点检查：

1. 完整文字修复过程只展示真实事件，不展示虚构推理或未发生步骤。
2. `TASK_FAILED` 失败码与证据来源严格匹配。
3. 上传资产必须属于当前用户，并满足 `APPROVED` 与 `NORMALIZED`。
4. 质量失败最多重试一次；二次失败无预览且不扣权益。
5. 生产路径保持 fail-closed，不使用 Mock 伪造成功。
6. TypeScript 源文件与微信运行时 JavaScript 同步。
7. 不泄露 Token、原图地址、供应商原始响应或隐藏推理。

Critical 和 Important 必须修复，并重新运行完整 CI。Minor 写入后续任务，不阻塞本阶段。独立复审超时、中断或未返回不能记作通过。

## 6. PR 转 Ready 条件

只有同时满足以下条件，才可将 PR 从 Draft 转为 Ready：

- GitHub CI 全绿。
- 独立复审无未解决 Critical 或 Important。
- 本地 HEAD、远程功能分支 SHA 和 PR head 一致。
- 本地工作树干净。
- PR 描述继续明确真实模型、MySQL/COS、微信 IDE/真机和发布尚未验收。

转为 Ready 不等于合并授权。本阶段不自动合并；是否合并由用户另行决定。

## 7. 失败处理与回滚

- CI 失败时 PR 保持 Draft，先在本地复现并定位根因，再做最小修复。
- 新增工作流独立成提交；如果 GitHub runner 与项目不可兼容，可通过普通 revert 回退，不重写历史、不强推。
- 若第三方 Action 的 SHA、许可证或供应链来源无法核验，停止实施并报告，不改用未知 Action 或下载脚本。

## 8. 验收标准

- 工作流配置经过语法与静态安全检查。
- PR 实际出现 CI 检查且完整运行全部五项门禁。
- 日志准确显示测试 passed/skipped/failed 数量，并保留真实环境 `NOT ACCEPTED` 边界。
- 独立复审形成可追溯结论，无未解决 Critical/Important。
- 满足全部 Ready 条件后才转换 PR 状态；不自动合并。
